Decisão de arquitetura: LLM atrás de proxy com token

O desenho original previa o LLM com ingress interno. A assinatura Azure for Students, porém, só recebe ambientes Container Apps no modo Express, que não tem descoberta de serviços internos (apps conversam pela URL pública). Testamos criar um ambiente Standard em todas as regiões permitidas pela política da assinatura e a Azure recusou em todas:

brazilsouth, chilecentral, northcentralus, spaincentral, belgiumcentral:
ManagedEnvironmentModeNotSupported: The managed environment mode Standard is not currently available in this region.

Solução adotada, mantendo os dados no Brasil: o Ollama (que não tem autenticação) escuta só em 127.0.0.1 dentro do container, e um proxy Caddy na porta 8080 exige Authorization: Bearer <token>, respondendo 401 a qualquer outra chamada. O token (48 caracteres aleatórios) é gerado pelo Terraform (random_password), entregue aos dois apps como secret do Container Apps e nunca aparece no código, na imagem ou no GitHub. O container recusa iniciar se o token tiver menos de 32 caracteres.

4. Pipeline DevSecOps 4,0 pts

Workflow devsecops.yml, disparado em todo push e pull request. Deploy apenas na main, no Environment production.

EtapaFerramentaBarra o pipeline quando…
1. SegredosGitleaks (histórico completo)encontra credencial em qualquer commit
2. SASTSemgrep (p/python, p/dockerfile, p/terraform)há achado nas regras
3. BuildDockera imagem não compila
4. VulnerabilidadesTrivy imagem (SO + bibliotecas) e Trivy config (Dockerfile/Terraform)CVE HIGH/CRITICAL com correção disponível, ou má configuração HIGH/CRITICAL
5. PublicaçãoGHCR (tag = SHA do commit)—
6. DeployTerraform fmt → validate → plan → apply, login OIDCformatação, validação ou apply falham
7. Teste de fumaçacurl /health na URL publicadaa API não responde

Segredos em GitHub Secrets

AZURE_CLIENT_ID, AZURE_TENANT_ID, AZURE_SUBSCRIPTION_ID, ALERT_EMAIL (e, opcionalmente, DATABRICKS_*). O login na Azure usa OIDC: não há senha de service principal guardada em lugar nenhum. Nomes não sensíveis (resource groups, storage do state) ficam em GitHub Variables.

Execução barrada → corrigida

Barrada: commit com credencial AWS falsa na branch demo/segredo-vazado. O Gitleaks detectou aws-access-token e generic-api-key; build e deploy nem executaram. {{RUN_BLOCKED}}

RuleID: aws-access-token   File: app/config_demo.py   Line: 2
RuleID: generic-api-key    File: app/config_demo.py   Line: 3
WRN leaks found: 2
Gitleaks: failure · Semgrep: success · Build + Trivy: skipped · Deploy: skipped

Corrigida: credencial removida e histórico da branch reescrito; o pipeline volta a passar. {{RUN_FIXED}}

Também barrado durante o desenvolvimento: o Trivy reprovou a imagem por 2 CVEs HIGH no zlib1g da base Debian; a correção foi aplicar apt-get upgrade no Dockerfile (resultado: 0 HIGH/CRITICAL).

9. Reprodutibilidade

O README traz o passo a passo completo: rodar local com docker compose up --build; criar a base da nuvem com infra/bootstrap.sh (resource groups, state remoto, identidade OIDC); cadastrar Secrets/Variables; e publicar com um git push na main.

Limitações conhecidas

  • LLM em CPU: respostas de 10–30 s; a primeira após inatividade pode levar 1–2 min (escala a zero). O modo demo do assistente não depende do LLM.
  • Modos LoRA não estão na imagem de produção (dependem de PyTorch); a API responde 503 com mensagem clara.
  • Sem credenciais do Databricks, o dashboard usa o snapshot histórico documentado.
